# Shed: the test domains

A neighbourhood tool shed, invented to drive the library with no word of q- (LIB-2). Members borrow, reserve and return tools; a keeper manages the catalogue and the repairs; a visitor browses the catalogue.

| domain                                            | language                                                                         | kind                                                          |
| ------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `business/tools`                                  | tool; added, retired, under repair; a sheet of tools loaded                      | business, upstream                                            |
| `business/loans`                                  | loan, reservation, return (on time, late, damaged)                               | business, downstream, its own view of the tools (V11)         |
| `persona/visitor`, `member`, `keeper`, `workshop` | who browses, who borrows, who keeps the shed, who repairs its tools from outside | persona, one domain per hat, with the values of auth (DOM-25) |
| `auth/accounts`                                   | account, key, hat, member card                                                   | auth: lookups over its adapters' data (PER-9, D43)            |

The library reasons by tree and knows no domain: a component is an export built by a builder of the library (`fact`, `command`, …: every builder, and every component of the file's own folder, comes by name from the generated scope of the kind the file builds (`import { command, fact } from './_scope_command.ts'`), bound to the context of that point and layered so that no import goes round), found by the generator, and its path is its folders, the kind its builder gives and its name (`business/tools/fact/a_tool_has_been_added`); the tree is the folders [`sight.ts`](sight.ts) names and every folder below them (`business/tools/`; `adapter/` is outside it, as a folder of service prefixed with `@` inside it), and in them the files are the author's choice, `x.ts` the author's and `_x.ts` the generator's, its twin, which the code imports (DOM-25). A domain is the architecture's: a folder in the folder of its kind. Who sees what of whom is a map, [`sight.ts`](sight.ts), the architecture's and not the library's (LIB-1): the generator writes in each folder seen a door per audience (`_door_persona.ts`), and in the scopes of the folders that see it that door, under the folder's name (`tools.id.tool_id`). No business domain sees of another more than its identities (GR-3, V11, DOM-24); a persona sees of a business domain its use cases, identities and facts and nothing else (GR-1, DOM-16), of auth its lookups and identities (PER-9); a reaction, which sits above the domains in `reaction/`, a folder per procedure, the facts and use cases of the business (GR-9): `loans` has its own view of the tools, keyed by the `tool_id` of `tools`, and the adapters link it to `tools`. The twins brand identities, facts, predicates and selection predicates with their path; `_registry.ts` lists each path with its component, for the library to find a path at runtime (DOM-24). Formats (`date_time`, `day`) are the library's. [`adapter/sql.ts`](adapter/sql.ts) is a sketch of a SQL state adapter; [`adapter/memory/`](adapter/memory/) a sketch of the in-memory oracle, the reference interpreter (TST-2, V10), one module per domain, whose imports show who reads whom, with its reads typed by subject (DOM-18).

Shed imports the library, `domains/src/library/` (zen0), since part 7.5 of [the plan](../../../../docs/plan.md), under the name `zz` (A, 19 Nov 2026: DOM-25, "The library's name in Shed"). Until then it imported `wlib.ts`, the wished library: the types and signatures the domains wanted from the library, without bodies, the requirement of the library steps (3–7) once Shed held every scenario in scope (step 2), each run against the [catalogue of the scenarios](../../../../docs/scenarios.md); each step moved its part into the library, and the file was deleted when the library was whole. [`configurator.ts`](configurator.ts) wires the shed on the oracle: its trees, the effect executor of `loans`, the consumers of every reaction (CFG-1, "The shed's configurator, at runtime").

The scenarios of the [catalogue](../../../../docs/scenarios.md) run as tests on the oracle in [`scenarios/`](scenarios/), one file each (`sc-<nn>.test.ts`), over the harness [`scenarios/oracle.ts`](scenarios/oracle.ts): one cell of the in-memory adapter, the ports the library builds over it, the clock and the ids injected (TST-2, TST-3); a scenario observes what the ports give, never the cell's state. ## Experiments

Shed tries different approaches to the same question, one per domain, to compare them before one becomes a rule in [`architecture.md`](../../../../docs/architecture.md).

| question            | `tools`                                                                                                                                                                                                     | `loans`                                                                                                                                                                                                                                                                                                                                                        | personas |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| a value with states | by subtraction: a schema with every field of every state, each state `.extend`s it with its discriminant and marks the fields it lacks `absent` (`?: undefined`); a discriminated union of compatible types | by nesting: the fields every state shares stay flat; the state is one field, a discriminated union of states with only their own fields (`loan.progress`); a state of the whole is the schema `.extend`ed with one state (`ongoing_loan`); a fact that changes the state writes the new state whole (`returned_loan.pick({ id, progress })`), with no `absent` |          |

### A value with states: subtraction and nesting compared (step 3)

- **Nesting** (`loans`) gives honest types: a stage has only its own fields, a field of a stage reads only after narrowing on `progress.stage`; no `absent`. A transition writes the new stage whole, so an adapter has one rule for it (replace `progress`). Its limit: the creator does not read the state, so a fact can write only what it knows (input, context, constants); a field that must survive a transition belongs to the common part. Reading "the return date, if any" in a list needs narrowing or a `dsl` function.
- **Subtraction** (`tools`) lets any field read without narrowing, and a fact picks the fields it changes and leaves the others; the types carry `?: undefined` for the fields a state lacks.
- How many levels (A, 13 Nov 2026 (3)): the domain's view decides, never the cost of a change. Picture the domain as an office, with its workflows, its priorities and the forms designed for its role: a stage is where the office's handling of the case changes; a mark that leaves the handling as it was is a sub-state inside the stage. An overdue loan is still handled as one the member has (lent tools are not lent again, the return desk takes it back alike), so `overdue` is a stamp on the card, `progress.term` in `ongoing`; a loan declared lost, which nobody expects back any more, would be a stage beside `returned`.
- Reading so far: nesting for values with a life cycle in stages (loans, reservations: processes, DOM-19); subtraction for catalogue entries, where most fields are shared and states differ by a few. No rule yet: the test is step 9, when `tools` gains `underRepair`, a state with data of its own in the middle of a life cycle.
